# Поиск по справочнику отвечает за 800–900 мс

Status: ready-for-human

## Что происходит

`search_ingredients` — путь маппинга распознанных ингредиентов. Он вызывается на
КАЖДУЮ позицию блюда, то есть десять ингредиентов складываются в девять секунд
ожидания.

Замер на живой базе (сетевой канал до Огайо — 185 мс, для сравнения
`search_dishes` в том же прогоне отвечает за 280 мс):

| | до правки «ё» | после |
|---|---|---|
| «лук репчатый» | 845 мс | 1006 мс |
| «chicken breast» | 738 мс | 954 мс |
| «куриная грудка» | 815 мс | 1097 мс |

То есть ~800 мс появились ДО правки про «ё» — их принёс импорт 122 607 блюд
Povarenok. Сама «ё» добавила примерно четверть сверху. После индексов из 0013 —
870–930 мс.

## Причина

Триграммный индекс построен по всей таблице, а фильтр по `kind` применяется уже
после чтения строк с диска. EXPLAIN, запрос «куриная грудка» с
`kind = 'ingredient'`:

```
Bitmap Index Scan on ingredients_name_ru_idx … rows=8884
Rows Removed by Index Recheck: 8324
Rows Removed by Filter: 525          ← отсев по kind
Heap Blocks: exact=4042              ← 4042 страницы ради 35 строк
Execution Time: 363 ms
```

Сырья 8265 строк, блюд 128 040. Поиск по сырью вычитывает в шестнадцать раз
больше мусора, чем полезного.

## Что уже проверено

**Частичный индекс решает задачу — 15.9 мс вместо 363**, в 23 раза. Проверено
EXPLAIN'ом с литералом и с константным массивом, оба варианта его берут.

**Но внутри функции он не работает**: `kinds` там параметр, а не литерал, и
планировщик не может доказать предикат частичного индекса. Замер после создания
частичных и составного (`btree_gin` по `(kind, name_ru)`) индексов показал: время
функции не изменилось. Индексы удалены миграцией 0014 как мёртвый груз.

**Не помогло:** дополнительные btree по выражениям ярусов `exact`/`head` — они
уже существовали с миграции 0005, я создал дубликаты и удалил их там же.

## Что делать

Переписать `search_ingredients` с ветвлением по частому случаю
`kinds = array['ingredient']`: в этой ветке предикат становится литеральным,
частичный индекс — доказуемым. Плюс вернуть частичные индексы.

Обязательное условие: замер до и после по реальным запросам из
`recognition_items`, как это сделано для «ё» (см. `.scratch/russian-dish-catalog`,
тикет 08). На этом пути стоят H1 и H2.


## Что сделано

Миграция 0015: отдельная функция `search_raw_ingredients` с зашитым
`kind = 'ingredient'`, синонимы вынесены из цепочки OR в ветку union,
частичные триграммные индексы по kind. `match.ts` переключён на неё.

Замер (выдача сверена построчно со старой — расхождений 0):

| запрос | было | стало |
|---|---|---|
| мед | 1005 мс | 564 мс |
| лук репчатый | 1096 мс | 751 мс |
| chicken breast | 831 мс | 527 мс |
| куриная грудка | 999 мс | 650 мс |
| творог | 815 мс | 528 мс |

Канал до Огайо в этом прогоне — 290 мс, то есть время запроса упало примерно
вдвое. Это меньше, чем обещали первые замеры, и почему — ниже.

## Чего НЕ хватило и что мерить дальше

Первая оценка «в десять раз» была снята на упрощённом теле функции (два яруса,
без синонимов) и оказалась завышенной. Настоящая картина сложнее, и главное в
ней — вот что.

**Корень был не в `kind`, а в форме условия.** EXPLAIN показал, что планировщик
выбирал обход по индексу `kind` и считал similarity фильтром на всех 8265
строках сырья: `exists` по синонимам внутри OR не давал сложить триграммные
условия в bitmap. Частичные индексы по kind — правильная, но вторичная мера;
сами по себе они не помогали.

Три подхода, которые НЕ сработали, чтобы их не проходили заново:

1. Просто создать частичные индексы — время не менялось даже после
   пересоздания функции (то есть дело не в кэше планов).
2. Собирать предикат динамически через EXECUTE: `kind in ('ingredient')`
   планировщик к равенству не сводит, ускорения нет, а смешанный поиск
   деградировал с 900 мс до 5 секунд.
3. Поднять `pg_trgm.similarity_threshold` в теле функции — Supabase не даёт
   прав на этот параметр.

Остаток (~250–450 мс) не разобран. Следующий шаг — снять EXPLAIN уже с новой
функции по ярусам и посмотреть, берутся ли частичные индексы в ветке
`fuzzy_by_name` и сколько стоит вычисление `ru_norm` на кандидатах.

**Смешанный поиск не ускорен.** `search_ingredients` с двумя видами (экран
«добавить из справочника») остаётся на прежних ~900 мс: под предикат
`kind = any(...)` частичный индекс не подходит.
