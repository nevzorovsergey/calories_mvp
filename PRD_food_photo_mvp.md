# PRD: Прототип распознавания состава и калорийности блюда по фотографии

**Версия:** 1.2 (MVP)
**Дата:** 26 июля 2026
**Статус:** к реализации
**Тип продукта:** внутренний исследовательский прототип (PWA), закрытый круг пользователей

---

## 1. Цель и гипотезы

### 1.1 Цель прототипа

Собрать работающий инструмент, который позволит накопить размеченный датасет «фото → что распознала модель → что исправил человек» и на нём измерить, насколько применимо распознавание состава и калорийности блюд по фото.

Прототип **не** оптимизируется под точность, красоту или продакшн-нагрузку. Он оптимизируется под **качество собираемых данных** и **скорость проверки гипотез**.

### 1.2 Проверяемые гипотезы

| № | Гипотеза | Как измеряем |
|---|---|---|
| H1 | LLM распознаёт состав блюда достаточно хорошо, чтобы пользователю было проще поправить, чем ввести вручную | Доля ингредиентов, оставленных без изменений; число добавленных/удалённых позиций |
| H2 | Основная ошибка — в весе, а не в составе | Сравнение отклонения по составу (precision/recall) и по массе (MAPE) |
| H3 | Разные модели дают заметно разное качество при разной цене | Сравнение моделей на одних и тех же фото против пользовательской правки |
| H4 | Наличие эталонного объекта в кадре улучшает оценку массы | Сравнение MAPE массы на фото с эталоном и без |
| H5 | Пользователь готов регулярно править состав, а не бросает после 2–3 раз | Retention по дням, доля сохранённых приёмов пищи с правками |
| H6 | Принуждение модели к явной масштабной цепочке улучшает оценку массы | A/B двух версий промпта на одних фото (§7.5.5) |

### 1.3 Ключевой продуктовый принцип

Модель **никогда не выдаёт итоговую цифру как истину**. Она выдаёт **гипотезу о составе**, которую человек подтверждает или правит. Обе версии сохраняются навсегда и никогда не перезаписывают друг друга.

## 2. Границы (что НЕ входит в MVP)

Не делаем:
- Depth/LiDAR, ARKit/ARCore, монокулярную оценку глубины (только фиксируем факт наличия эталона в кадре).
- Автоматическую метрологию по эталонному объекту (детекция монеты/карты через OpenCV). Только запись факта.
- Штрихкоды, распознавание упаковок, импорт из меню ресторанов.
- Интеграции с носимыми устройствами, Apple Health, Google Fit.
- Рекомендации по питанию, цели по калориям, дефицит/профицит, коучинг.
- Регистрацию пользователей, восстановление пароля, соцлогин.
- Юридический слой: GDPR, 152-ФЗ, политики, дисклеймеры, согласия.
- Монетизацию, платежи, тарифы.
- Офлайн-режим (кроме базовой PWA-оболочки и кэша статики).
- Мобильные нативные приложения, публикацию в сторах.
- Локализацию (только русский интерфейс; английский — только как внутренние канонические названия).

## 4. Технологический стек

### 4.1 Рекомендуемая связка

| Слой | Решение | Почему | Бесплатный лимит (июль 2026) |
|---|---|---|---|
| **Фронтенд + бэкенд** | Next.js (App Router) на **Vercel Hobby** | PWA из коробки, серверные route handlers прячут ключ polza.ai, деплой из git, pay-as-you-grow | 100 ГБ трафика, 1 млн вызовов функций, 4 CPU-часа активного CPU, макс. длительность функции 300 с |
| **БД + Auth + Storage** | **Supabase Free** | Postgres + встроенная авторизация + хранилище файлов + табличный редактор в дашборде (можно завести пользователей руками), REST/JS SDK | 500 МБ Postgres, 1 ГБ файлов, 5 ГБ egress, 50 000 MAU, 2 проекта |
| **LLM** | **polza.ai** | OpenAI-совместимый API, оплата рублями, возвращает стоимость в ответе | pay-as-you-go, бесплатных лимитов нет (есть бесплатные модели вроде T-Pro, но они не мультимодальные) |

Важно: **время ожидания ответа LLM не расходует активное CPU на Vercel** — биллинг идёт по фактическому CPU, а ожидание I/O не считается. Это делает Hobby-план пригодным для проксирования LLM-запросов.

### 4.2 Альтернативы (если основной вариант не подойдёт)

| Вариант | Плюсы | Минусы |
|---|---|---|
| Cloudflare Pages + Workers + D1 + R2 | Щедрее лимиты по хранилищу (R2 — 10 ГБ), нет проблемы «засыпания» | D1 — SQLite, слабее для аналитических запросов; нет готового Auth |
| Render/Railway + Neon (Postgres) + Cloudflare R2 | Обычный long-running сервер, нет таймаутов функций | Больше ручной настройки, free-инстансы засыпают |
| Timeweb Cloud / Selectel / Yandex Cloud | Доступность из РФ гарантирована, оплата рублями | Нет бесплатных лимитов уровня Supabase, больше DevOps |

### 4.3 Ограничения выбранного стека, которые надо учесть

1. **Supabase Free засыпает** после 7 дней без запросов к БД. Обязательно поставить cron-пинг (Vercel Cron раз в 3 дня или GitHub Actions по расписанию).
2. **Vercel Hobby — только некоммерческое использование.** Для внутреннего теста это в порядке; при первом намёке на монетизацию — переезд на Pro ($20/мес).
3. **1 ГБ хранилища** ≈ 3000–5000 фото при сжатии до 1024 px / JPEG q0.8. Для прототипа достаточно; заложить job очистки оригиналов старше N дней.
4. **500 МБ Postgres** — с запасом, если не хранить в БД сами картинки (не хранить!) и не раздувать `raw_response` бесконтрольно (хранить, но при необходимости — сжимать/архивировать старые).
5. **Доступность из РФ.** Если тестировщики в России и Vercel/Supabase будут недоступны — план Б: перенос на Timeweb Cloud. Проверить в самом начале, до написания кода.

### 4.4 Фронтенд

- React + Next.js App Router, TypeScript.
- UI: Tailwind CSS v4 + **Konsta UI v5** (MIT, iOS-тема, поддержка Next.js SSR). Мобильный-first, вертикальная компоновка. Подробнее — §13.
- PWA: `manifest.json`, service worker (кэш статики), иконки, `display: standalone`. Устанавливается на домашний экран на iOS и Android.
- Камера: `<input type="file" accept="image/*" capture="environment">` — работает и в Safari iOS, и в Chrome Android без нативного кода.
- Сжатие на клиенте перед отправкой: `canvas` → longest side 1024 px → JPEG quality 0.8. Это снижает и стоимость токенов, и трафик.

## 5. Архитектура и поток данных

### 5.1 Поток «сделать фото → получить состав»

```
[PWA] снимок с камеры
   ↓ клиентское сжатие (1024px, JPEG q0.8)
[PWA] POST /api/meals  (multipart: image + hints)
   ↓
[API] 1. auth-проверка (Supabase JWT)
      2. загрузка оригинала и сжатой копии в Supabase Storage
      3. запись meals (status = 'processing')
      4. вычисление sha256 сжатого изображения
      5. чтение активной модели из config
      6. вызов polza.ai /v1/chat/completions
         - image как data:image/jpeg;base64,...
         - response_format: json_schema, strict: true
         - без chain-of-thought (см. §7.1)
      7. запись recognitions (raw_response, usage, latency)
      8. расчёт стоимости: cost_rub из ответа + cost_direct (§9)
      9. маппинг ингредиентов на справочник (§8.4)
     10. расчёт нутриентов по каждому ингредиенту и итогу
     11. создание первичной версии meal_items (source='model')
      ↓
[PWA] GET /api/meals/{id} → экран правки
```

Синхронный вызов допустим: 300 с лимита Vercel Hobby с большим запасом покрывают 10–40 с на vision-запрос. Если модель начнёт таймаутить — переключиться на схему «задача + polling» (в `meals` уже есть `status`, менять почти нечего).

### 5.2 Изображения

Храним **две** версии:
- `original` — как пришло с устройства (для будущих экспериментов, можно удалять по расписанию).
- `sent` — ровно те байты, которые ушли в модель, плюс `sha256`. Это обязательное требование воспроизводимости: при повторном прогоне другой моделью отправляем **тот же самый** файл.

Передача в polza.ai: base64 внутри запроса. Это надёжнее, чем signed URL (не зависит от доступности Supabase Storage снаружи и от срока жизни ссылки). Для файлов > 3–4 МБ — использовать `/v1/storage/upload` polza.ai, но при сжатии до 1024 px этого не потребуется.

## 6. Конфигурация моделей

Конфиг живёт в файле в репозитории (`config/models.ts`) и дублируется в таблицу `model_configs` при деплое — так его видно из SQL при анализе.

```ts
export const MODELS_CONFIG = {
  // модель, которая вызывается автоматически в момент фотографирования
  defaultModelId: "google/gemini-3-flash",

  // все модели, доступные для ручного перепрогона и сравнения
  models: [
    {
      id: "google/gemini-3-flash",
      label: "Gemini 3 Flash",
      vendor: "google",
      enabled: true,
      imageDetail: "high",        // low | high | auto — влияет на цену
      maxTokens: 4000,
      temperature: 0.2,
      promptVersion: "v2-scale",   // v1-plain | v2-scale — см. A/B в §7.5.5
      // официальные цены вендора для расчёта «сколько было бы напрямую»
      vendorPricing: {
        currency: "USD",
        promptPerMillion: 1.50,
        completionPerMillion: 7.50,
        cachedPromptPerMillion: 0.15,
        source: "ai.google.dev/pricing",
        checkedAt: "2026-07-26"
      }
    },
    { id: "openai/gpt-5.1", label: "GPT-5.1", vendor: "openai", enabled: true, /* ... */ },
    { id: "anthropic/claude-sonnet-5", label: "Claude Sonnet 5", vendor: "anthropic", enabled: true, /* ... */ },
    { id: "qwen/qwen3-vl-235b-a22b", label: "Qwen3-VL 235B", vendor: "alibaba", enabled: true, /* ... */ },
    { id: "x-ai/grok-4-vision", label: "Grok 4 Vision", vendor: "xai", enabled: false, /* ... */ }
  ]
};
```

**Требование к реализации:** точные `id` моделей взять из живого каталога polza.ai, а не из этого примера:

```bash
curl "https://polza.ai/api/v1/models/catalog?inputModalities=image&type=chat&sortBy=price&sortOrder=asc" \
  -H "Authorization: Bearer $POLZA_KEY"
```

Оттуда же при деплое забирать актуальные `pricing.prompt_per_million` / `completion_per_million` (RUB) и складывать в `model_pricing_snapshots` — это защита от того, что polza.ai поменяет тарифы и старые расчёты «поедут».

**FR-CONF-1.** Смена `defaultModelId` не требует изменения схемы БД и миграций.
**FR-CONF-2.** Каждая запись `recognitions` хранит `model_id` и `prompt_version` — при смене промпта старые результаты остаются интерпретируемыми.
**FR-CONF-3.** Модель с `enabled: false` не показывается в списке ручного перепрогона, но её прошлые результаты остаются в истории.

## 7. Контракт с моделью

### 7.1 Принципы промпта

Учитываем выводы предыдущего ресёрча:
- **Никакого свободного chain-of-thought.** Прямой structured output. Просить «рассуждай пошагово текстом» — значит терять 3–8 п.п. точности на перцептивных задачах у моделей меньшего размера. Оговорка: это относится к *свободному* рассуждению. Структурированные числовые промежуточные поля (масштабная цепочка, §7.5) — другой инструмент, и его эффект мы проверяем отдельным A/B.
- `strict: true` в `json_schema`, `additionalProperties: false` — иначе разбор ответа превращается в защиту от произвола.
- `temperature: 0.2` — детерминированность важнее креативности.
- Просим **и** оценку модели по нутриентам, **и** голый состав. Нутриенты потом считаем сами по справочнику, но модельную оценку сохраняем как отдельную колонку для сравнения (см. §8.5). Это почти бесплатно и даёт лишнюю ось анализа.
- Отдельно просим перечислить **объекты-эталоны масштаба** в кадре — это ядро гипотезы H4.

### 7.2 Системный промпт (v1)

```
Ты — эксперт по составу блюд и нутрициологии. Тебе показывают фотографию еды.

Твоя задача — разобрать блюдо на ингредиенты и оценить массу каждого.

Правила:
- Названия ингредиентов давай ОДНОВРЕМЕННО на русском (name_ru) и на английском (name_en).
  Английское название должно быть каноничным термином продуктовой базы (например
  "chicken breast, roasted", "olive oil", "white rice, cooked"), а не описательной фразой.
- Массу указывай в граммах для съедобной части, БЕЗ учёта посуды, костей, кожуры,
  которые не съедаются.
- Разделяй ингредиенты, которые пользователь может захотеть править отдельно
  (мясо, гарнир, соус, масло для жарки). Не сваливай всё в один пункт.
- Обязательно включай невидимые, но почти наверняка присутствующие ингредиенты
  (масло, сахар, соль) — помечай их флагом visible: false.
- Не рассуждай в ответе. Верни только JSON по заданной схеме.

ОПРЕДЕЛЕНИЕ МАСШТАБА — выполняй строго в этом порядке:
1. Найди в кадре предметы известного размера: банковская карта, монета, линейка,
   столовые приборы, смартфон, наручные или фитнес-часы, ладонь, стандартная посуда.
   Перечисли ВСЕ найденные в scale_references с нормализованными координатами рамки.
2. Если такой предмет найден — ты ОБЯЗАН построить на нём оценку размеров:
   - определи его видимый размер как долю ширины кадра (apparent_fraction);
   - зная его реальный размер в мм, вычисли масштаб (мм на долю кадра);
   - через этот масштаб оцени размеры посуды и порции;
   - заполни блок scale_chain числами, которые ты реально использовал.
   Установи scale_mode = "reference".
3. Если подходящего предмета нет, но видна посуда — оцени размер посуды по типовым
   значениям и установи scale_mode = "container".
4. Если нет ни того, ни другого — оценивай по общему представлению о типичной порции
   и установи scale_mode = "prior".

Числа в scale_chain должны быть согласованы между собой и с итоговой массой.
Не подгоняй scale_chain под заранее придуманный ответ — сначала цепочка, потом масса.
```

Пользовательское сообщение = изображение + опциональная подсказка от пользователя + (если у пользователя настроены эталоны, §7.5) строка вида: `В кадре может присутствовать: банковская карта (ширина 85.6 мм), Apple Watch 45 мм (высота корпуса 45 мм). Используй эти точные размеры, не угадывай их.`

### 7.4 Обработка ошибок

**FR-LLM-1.** Если модель вернула невалидный JSON или ошибку API — `recognitions.status = 'failed'`, `error_text` сохраняется, пользователю показывается «Не получилось распознать» с кнопками «Повторить» и «Ввести вручную».
**FR-LLM-2.** Одна автоматическая повторная попытка при 5xx/таймауте. Больше — нет: это исказит статистику по стоимости.
**FR-LLM-3.** Неудачные попытки тоже пишутся в `recognitions` (с их стоимостью, если она была списана) — иначе экономика будет занижена.

### 7.5 Как на самом деле работает определение масштаба

Это самый принципиальный раздел документа, поэтому — подробно.

#### 7.5.1 Что модель НЕ делает

Мультимодальная модель не выполняет фотограмметрию. Она не измеряет пиксели, не строит пропорцию «монета : тарелка» и не решает уравнение. Она сопоставляет картинку с образами, виденными при обучении, и выдаёт правдоподобное число.

Отсюда два следствия, которые надо принять до написания кода:

1. **Инструкция «используй монету для масштаба» не включает никакого механизма.** Она смещает распределение ответов — иногда в нужную сторону, иногда нет. Это влияние, а не управление.
2. **Самоотчёт модели о собственных действиях недостоверен.** Поле вида «использовал ли ты этот объект» — это не интроспекция, а post-hoc рационализация: модель отвечает то, что выглядит уместным ответом, а не то, что происходило внутри. Верить голому `used_for_scale = true` нельзя.

Именно поэтому в версии 1.0 этот флаг был бесполезен, и вы правильно на нём споткнулись.

#### 7.5.2 Три способа это починить

| Подход | Суть | Достоверность | Сложность |
|---|---|---|---|
| **A. Просто попросить** | «Если есть эталон — используй его» | низкая, непроверяемая | нулевая |
| **B. Внешняя цепочка** | Модель обязана вернуть промежуточные числа: реальный размер якоря → его видимая доля кадра → масштаб → размер посуды → объём → плотность → масса | средняя, но **проверяемая** | низкая |
| **C. Гибрид** | Модель возвращает только рамки объектов (bbox), арифметику масштаба считает бэкенд | высокая | средняя |

**В MVP реализуем B, закладывая переход к C.**

Почему B, а не сразу C: bbox-грудинг поддержан не всеми моделями одинаково (Gemini и Qwen-VL умеют, остальные — по-разному), а нам нужно сравнивать модели на равных. Поэтому bbox мы **запрашиваем** (поле есть в схеме), но пока используем как диагностику, а не как основу расчёта.

Ключевое преимущество B над A: **цепочку можно проверить арифметически, не имея ground truth.** Бэкенд после получения ответа считает:

```
ожидаемый_масштаб = anchor_real_mm / anchor_apparent_fraction
                    ≈ mm_per_frame_width          (расхождение > 15% → флаг)

ожидаемый_объём  = π * (food_footprint_mm/2)² * food_mean_height_mm / 1000
                    ≈ estimated_volume_ml         (расхождение > 30% → флаг)

ожидаемая_масса  = estimated_volume_ml * assumed_density_g_per_ml
                    ≈ total_weight_g              (расхождение > 25% → флаг)
```

Если числа между собой не сходятся — значит модель заполнила цепочку декоративно, а массу взяла «из головы». Это фиксируется в `scale_chain.consistency_flags` и становится **измеримой характеристикой модели**: одни модели считают согласованно, другие имитируют. Такой метрики нет ни в одном публичном бенчмарке, и она напрямую отвечает на ваш вопрос «учитывала ли она эталон на самом деле».

**FR-SCALE-1.** Бэкенд выполняет три проверки согласованности после каждого распознавания и сохраняет результат в `recognitions.scale_chain`.
**FR-SCALE-2.** `scale_mode` из ответа денормализуется в отдельную колонку — это основная ось анализа гипотезы H4.

#### 7.5.3 Вторая проверка: правильный ли размер приписан эталону

Даже если цепочка согласована, модель может ошибиться в исходной константе — принять российскую 10-рублёвую монету за 30 мм вместо 22 мм, и вся цепочка поедет пропорционально.

Это тоже проверяемо, потому что реальные размеры эталонов известны точно:

| Эталон | Истинный размер | Надёжность |
|---|---|---|
| Банковская карта | **85.60 × 53.98 мм** (ISO/IEC 7810 ID-1) | идеальная — стандарт един для всего мира |
| Монета 10 ₽ | 22.0 мм | зависит от страны и номинала |
| Монета 5 ₽ | 25.0 мм | то же |
| Монета 1 € | 23.25 мм | то же |
| Apple Watch (корпус) | 41 / 45 / 49 мм | надо знать модель |
| Линейка | по разметке | идеальная |

Отсюда вывод, который меняет продуктовое решение: **банковская карта — лучший эталон в мире**, потому что её размер стандартизирован ISO и одинаков в любой стране. Монеты для географии «весь мир» плохи: модель должна сначала угадать страну и номинал.

**FR-SCALE-3.** Бэкенд сравнивает `assumed_size_mm` с истинным размером эталона (если он известен из профиля пользователя) и записывает относительную ошибку в `scale_size_error`. Это чистая, ни от чего не зависящая метрика точности распознавания эталона.

#### 7.5.4 Реестр эталонов пользователя

Логичное продолжение: **не заставлять модель угадывать константу, а сообщать её.**

При заведении пользователя (или в настройках) он один раз отмечает, что у него есть и что он обычно кладёт в кадр: банковская карта, конкретная модель часов, монета конкретного номинала, линейка. Это пишется в `user_reference_objects` с точным `true_size_mm`.

Дальше при каждом запросе в пользовательское сообщение подставляется строка: «В кадре может присутствовать: банковская карта (ширина 85.6 мм), Apple Watch 45 мм. Используй эти точные размеры, не угадывай их.»

Это убирает целый класс ошибок практически бесплатно и превращает `scale_size_error` в измеримую величину (иначе истинный размер неизвестен и сравнивать не с чем).

**FR-SCALE-4.** Реестр эталонов настраивается в профиле, минимум — чекбоксами по готовому списку с преднастроенными размерами. Пустой реестр допустим, тогда подсказка не подставляется.

#### 7.5.5 A/B: а помогает ли всё это вообще

Всё вышеописанное — гипотеза, а не факт. Требование «верни масштабную цепочку» частично противоречит принципу «никакого CoT» из §7.1, и вполне может ухудшить распознавание, а не улучшить.

Проверяем это тем же механизмом, что уже заложен для сравнения моделей:

- `prompt_version = "v1-plain"` — без блока про масштаб, без `scale_chain`;
- `prompt_version = "v2-scale"` — полный вариант из §7.2.

**FR-SCALE-5.** `promptVariant` выносится в конфиг модели наравне с `modelId`. Экран сравнения (§11.7) позволяет прогнать одно и то же фото одной и той же моделью в двух вариантах промпта.
**FR-SCALE-6.** В «Лаборатории» — отдельный срез: MAPE веса в разрезе `prompt_version × scale_mode × had_reference`.

Это, по сути, четвёртая гипотеза сверх исходных пяти: **H6 — принуждение модели к явной масштабной цепочке улучшает оценку массы.** Ответ на неё интересен сам по себе и в публичных бенчмарках его нет.

## 8. Справочник ингредиентов и нутриентов

### 8.1 Источник данных

**Ядро: USDA FoodData Central**, типы записей **SR Legacy** и **Foundation Foods** (~8 000 позиций). Причины: public domain (CC0) — никаких лицензионных вопросов; полные дампы для self-hosting — полный контроль; до 140 нутриентов, включая все витамины и минералы.

**Дополнение: FNDDS** — для готовых блюд и комбинированных позиций (там уже посчитанные survey-блюда, а не только сырые продукты).

**Опционально на будущее (не в MVP):** CIQUAL для европейских позиций, Open Food Facts для упакованных продуктов по штрихкоду.

### 8.2 Русификация

Единоразовая офлайн-процедура при подготовке справочника:
1. Выгрузить SR Legacy + Foundation в CSV.
2. Пакетно перевести `description` через LLM (батчами по 50, дешёвая модель) → получить `name_ru` + 2–4 синонима.
3. Ручная вычитка топ-500 самых частых продуктов (мясо, крупы, овощи, молочка) — именно они закроют 80% реальных приёмов пищи.
4. Результат — CSV → импорт в Supabase.

Это разовая работа на несколько часов, но она даёт полностью подконтрольный русскоязычный справочник, который дальше можно править руками через табличный редактор Supabase.

### 8.3 Набор нутриентов в MVP

Обязательны в MVP (пользователь запросил витамины и минералы сразу):

**Энергия и макро:** ккал, белки, жиры (в т.ч. насыщенные), углеводы (в т.ч. сахара), клетчатка.

**Витамины (13):** A (мкг RAE), D (мкг), E (мг), K (мкг), C (мг), B1 тиамин (мг), B2 рибофлавин (мг), B3 ниацин (мг), B5 пантотеновая (мг), B6 (мг), B7 биотин (мкг), B9 фолаты (мкг DFE), B12 (мкг).

**Минералы (10):** кальций, железо, магний, фосфор, калий, натрий, цинк, медь, марганец, селен.

Для каждого нутриента в справочнике `nutrients` хранится норма суточного потребления (`rdi_default`), чтобы показывать «% от суточной нормы». Норма — одна общая для всех (без учёта пола/возраста), это MVP.

### 8.4 Маппинг названий на справочник

Модель возвращает свободные названия. Алгоритм сопоставления, по шагам, до первого попадания:

1. **Точное совпадение** `name_en` (после нормализации: lowercase, убрать пунктуацию) с `ingredients.name_en` или с записью в `ingredient_aliases`.
2. **Триграммный поиск** (`pg_trgm`, оператор `%`, порог similarity ≥ 0.45) по `name_en` и `name_ru`.
3. **Не нашли** → `match_status = 'unmatched'`, нутриенты берём из модельной оценки (`kcal_per_100g` и др. из JSON), помечаем `nutrition_source = 'model'`.

**FR-CAT-1.** В экране правки у каждого ингредиента есть строка поиска по справочнику. Когда пользователь вручную выбирает правильную позицию для `unmatched`-ингредиента — автоматически создаётся запись в `ingredient_aliases`. Справочник самообучается на использовании.
**FR-CAT-2.** Ингредиенты с `nutrition_source = 'model'` визуально помечаются (например, иконкой «≈») — пользователь должен понимать, что эти цифры не из справочника.
**FR-CAT-3.** Векторный поиск (pgvector + эмбеддинги названий) — не в MVP, но схема БД не должна мешать его добавить.

### 8.5 Расчёт нутриентов

Для каждого ингредиента: `нутриент = (weight_g / 100) × значение_на_100г`.
Итог по блюду = сумма по ингредиентам.
Итог по дню = сумма по блюдам с `meal_date = D`.

**Сырое vs готовое:** в MVP используем значение как есть, но сохраняем `state` и `cooking_method` от модели. Коэффициенты уварки (USDA Cooking Yields) и сохранности витаминов (USDA Nutrient Retention Factors) — **вне MVP**, но поля под них закладываем в схему, чтобы потом не мигрировать.

**Двойной расчёт.** Для каждого распознавания храним два набора итогов:
- `nutrition_catalog` — посчитано по справочнику,
- `nutrition_model` — посчитано по цифрам, которые дала сама модель.

Это позволит потом отдельно ответить: справочник вообще что-то улучшает или модель сама считает не хуже?

## 9. Учёт стоимости

Это одно из явных требований, поэтому вынесено в отдельный раздел.

### 9.1 Фактическая стоимость (polza.ai)

Каждый ответ `/v1/chat/completions` содержит объект `usage`:

```json
{
  "usage": {
    "prompt_tokens": 1520,
    "completion_tokens": 890,
    "total_tokens": 2410,
    "cost_rub": 0.87,
    "cost": 0.87,
    "prompt_tokens_details": { "cached_tokens": 0 },
    "completion_tokens_details": { "reasoning_tokens": 0 }
  }
}
```

**FR-COST-1.** Сохранять `usage` целиком в `recognitions.usage_raw` (jsonb) плюс развёрнуто в отдельные колонки: `prompt_tokens`, `completion_tokens`, `cached_tokens`, `reasoning_tokens`, `cost_rub_actual`.

### 9.2 Гипотетическая стоимость «напрямую у вендора»

Считается на бэкенде сразу после ответа, по формуле:

```
cost_direct_usd =
    (prompt_tokens - cached_tokens) / 1e6 * vendorPricing.promptPerMillion
  + cached_tokens                  / 1e6 * vendorPricing.cachedPromptPerMillion
  + completion_tokens              / 1e6 * vendorPricing.completionPerMillion

```

**Валюты не смешиваем и никуда не конвертируем.** Фактическая стоимость хранится в рублях (так её отдаёт polza.ai), гипотетическая — в долларах (так её публикуют вендоры). Это две независимые метрики, обе полезны сами по себе: рубли отвечают на вопрос «сколько мы реально потратили», доллары — «дорогая ли эта модель по мировым меркам».

**FR-COST-2.** `vendorPricing` берётся из `config/models.ts` (§6) и снапшотится в строку `recognitions.vendor_pricing_snapshot` (jsonb) — чтобы изменение тарифов вендора не переписало историю.
**FR-COST-3.** Дополнительно снапшотить цены самой polza.ai из `/v1/models/catalog` (`prompt_per_million`, `completion_per_million` в RUB) в `model_pricing_snapshots` — раз в сутки. Это даёт возможность пересчитать стоимость независимо от того, что вернул `usage`.

**Следствие отказа от конвертации:** коэффициент наценки polza.ai (во сколько раз дороже, чем напрямую) автоматически не считается — для него нужен курс. Если он понадобится, достаточно вписать в конфиг одну константу `USD_RUB_MANUAL` и пересчитать разово при анализе. В приложении этого не делаем.

**Оговорка, которую надо держать в голове при анализе:** расчёт «напрямую» — приблизительный. polza.ai может маршрутизировать запрос через промежуточного провайдера с собственной токенизацией, а тарификация изображений у разных вендоров устроена по-разному (плитки, фиксированная стоимость за картинку). Считаем это оценкой порядка величины, а не точной цифрой.

### 9.3 Что показываем

- **Пользователю:** ничего. Стоимость его не касается.
- **Админу (экран «Лаборатория»):** стоимость одного распознавания и средняя по модели — двумя колонками, «факт, ₽» и «напрямую, $». Плюс суммарные расходы за период в рублях.

## 10. Модель данных

### 10.1 Схема (Postgres / Supabase)

```sql

  id            serial primary key,

  id                serial primary key,
  source            text not null,           -- 'usda_sr' | 'usda_foundation' | 'usda_fndds' | 'manual'

  name_ru           text not null,
  name_en           text not null,
  category          text,
  state             text,                    -- 'raw' | 'cooked' | 'unknown'

  yield_factor      numeric,                 -- коэффициент уварки, вне MVP
  is_active         boolean not null default true,
  created_at        timestamptz not null default now()
);
create index on ingredients using gin (name_ru gin_trgm_ops);
create index on ingredients using gin (name_en gin_trgm_ops);
```

### 10.2 Безопасность данных

Row Level Security (RLS) Supabase: каждый пользователь видит только свои `meals`, `recognitions`, `meal_items`, `weight_evidence`. Админ (`profiles.is_admin = true`) видит всё. Справочники (`ingredients`, `nutrients`) — read-only для всех аутентифицированных.

Ключ polza.ai живёт **только** в переменных окружения Vercel и никогда не попадает на клиент.

## 11. Функциональные требования по экранам

### 11.1 Вход

**FR-AUTH-1.** Экран: логин (email) + пароль, кнопка «Войти». Никакой регистрации, никакого восстановления пароля.
**FR-AUTH-2.** Регистрация в Supabase Auth отключена. Пользователи создаются вручную через дашборд Supabase, профиль (`display_name`) — там же в табличном редакторе.
**FR-AUTH-3.** Сессия сохраняется между запусками PWA (пользователь логинится один раз).
**FR-AUTH-4.** При первом входе — короткий экран «Мои эталоны»: чекбоксы по готовому списку предметов известного размера (банковская карта, линейка, монеты по номиналам, модели часов). Выбранное пишется в `user_reference_objects` с точными размерами из справочника констант (§7.5.4). Экран пропускаемый, доступен потом из настроек.

### 11.2 Главный экран «Сегодня»

**FR-HOME-1.** Крупная сводка за сегодня: калории, белки, жиры, углеводы. Витамины и минералы — под сворачиваемым блоком «Подробнее», с % от суточной нормы.
**FR-HOME-2.** Лента приёмов пищи за сегодня: миниатюра фото, название блюда, время, калории. Тап → детальный экран.
**FR-HOME-3.** Плавающая кнопка «Сфотографировать» — основное целевое действие.
**FR-HOME-4.** Переключение даты стрелками влево/вправо (за вчера, позавчера) без ухода в раздел истории.
**FR-HOME-5.** Приёмы пищи со `status = 'processing'` показываются в ленте с индикатором загрузки.

### 11.3 Съёмка

**FR-CAP-1.** Тап на кнопку открывает камеру устройства (`capture="environment"`). Разрешена и загрузка из галереи.
**FR-CAP-2.** После выбора фото — экран предпросмотра с необязательным полем «Подсказка (что это, как готовили)» и кнопкой «Распознать».
**FR-CAP-3.** На экране предпросмотра — ненавязчивая подсказка: «Положите рядом банковскую карту — оценка веса будет точнее». Именно карту, а не монету: её размер стандартизирован ISO и одинаков во всём мире, тогда как монету модель должна сначала опознать по стране и номиналу (§7.5.3). Подсказка одновременно и UX-помощь, и провокация к сбору данных для H4.
**FR-CAP-4.** Клиентское сжатие перед отправкой (1024 px, JPEG q0.8).
**FR-CAP-5.** Во время распознавания показывается название вызываемой модели — прозрачность важна для эксперимента.

### 11.4 Результат и правка

Ключевой экран продукта.

**FR-EDIT-1.** Шапка: фото, название блюда (редактируемое), общий вес (редактируемый), итоговые калории.
**FR-EDIT-2.** Список ингредиентов. По каждому: название, вес в граммах, калории. Тап разворачивает БЖУ и полную нутриентную панель.
**FR-EDIT-3.** По каждому ингредиенту доступно:
  - изменить вес (числовой инпут + быстрый слайдер);
  - заменить ингредиент (поиск по справочнику с автодополнением);
  - удалить;
  - у `unmatched` — обязательное предложение «Привязать к справочнику».
**FR-EDIT-4.** Кнопка «Добавить ингредиент» → поиск по справочнику → ввод веса.
**FR-EDIT-5.** Изменение общего веса **пропорционально пересчитывает** веса всех ингредиентов (с возможностью отменить пересчёт одним тапом). Это самый быстрый способ поправить главную ошибку модели.
**FR-EDIT-6.** Ингредиенты, помеченные моделью как `visible: false`, отображаются с отдельной пометкой («выведено логически») — пользователю проще решить, оставлять ли их.
**FR-EDIT-7.** Итоговая панель: калории, БЖУ, клетчатка + разворачиваемый блок из 13 витаминов и 10 минералов с абсолютными значениями и % от нормы.
**FR-EDIT-8.** Кнопка «Сохранить». При первом сохранении, **если пользователь что-либо менял**, показывается модалка «Откуда вес?» (§11.5).
**FR-EDIT-9.** Кнопка «Сохранить без изменений» (когда правок не было) — это тоже ценный сигнал: модель угадала.
**FR-EDIT-10.** Сохранение **не изменяет** `recognitions` и `recognition_items`. Пользовательская версия пишется в `meal_items` / `meal_removed_items` с проставленным `origin`.
**FR-EDIT-11.** Повторное редактирование сохранённого приёма пищи доступно всегда, из истории.

### 11.5 Модалка «Откуда вес?»

Показывается один раз на приём пищи, после первого сохранения с правками. Не более 15 секунд на заполнение.

**FR-WE-1.** Вопрос 1 — «Как вы определили вес?», один вариант из: взвесил на весах / указано на упаковке / указано в меню / сам готовил, знаю раскладку / мерная посуда / прикинул на глаз.
**FR-WE-2.** Вопрос 2 — «Был ли в кадре предмет для оценки масштаба?», множественный выбор из списка (монета, банковская карта, линейка, столовые приборы, смартфон, часы/фитнес-браслет, ладонь, стандартная тарелка, ничего). **Предзаполняется тем, что нашла модель в `scale_references`** — пользователю останется подтвердить или снять галочку.
**FR-WE-3.** Вопрос 3 — «Насколько уверены в весе?», шкала 1–5.
**FR-WE-4.** Любой вопрос можно пропустить кнопкой «Не знаю» — записывается `null`, не блокирует сохранение.

Предзаполнение из ответа модели — это важная деталь: оно даёт бесплатную разметку «модель увидела эталон / эталон реально был», то есть точность самой детекции эталонов.

### 11.6 Детальный экран приёма пищи

**FR-DET-1.** Фото, текущая (пользовательская) версия состава, итоги, дата и время.
**FR-DET-2.** Кнопка «Редактировать» → экран правки.
**FR-DET-3.** Блок «Что предложила модель» — сворачиваемый, показывает исходную версию с подсветкой отличий от пользовательской (изменённый вес, удалённые и добавленные позиции).
**FR-DET-4.** Кнопка **«Проверить другой моделью»** → выпадающий список моделей из конфига (`enabled: true`, исключая уже прогнанные) → запуск.
**FR-DET-5.** Кнопка «Удалить приём пищи».

### 11.7 Сравнение моделей

**FR-CMP-1.** После прогона второй и последующих моделей на экране появляется таблица сравнения: колонки — «Модель A», «Модель B», …, «Ваша версия»; строки — общий вес, калории, БЖУ, число ингредиентов.
**FR-CMP-2.** Ниже — построчное сравнение состава: какие ингредиенты назвала каждая модель, какие остались в пользовательской версии.
**FR-CMP-3.** По каждой модели показывается отклонение от пользовательской версии: Δ веса (г и %), Δ калорий (ккал и %), совпавшие/пропущенные/лишние ингредиенты.
**FR-CMP-4.** Перепрогон использует **тот же самый файл** (`photo_sent_path`), который отправлялся первой модели. Иначе сравнение недействительно.
**FR-CMP-5.** Перепрогон другой моделью **не меняет** пользовательскую версию и `primary_recognition_id`.

### 11.8 История

**FR-HIST-1.** Список дней, от новых к старым: дата, суммарные калории, БЖУ, число приёмов пищи, полоска миниатюр фото.
**FR-HIST-2.** Тап на день → лента приёмов пищи этого дня.
**FR-HIST-3.** Из любой точки истории доступно редактирование приёма пищи.
**FR-HIST-4.** Простой график калорий по дням за последние 14 дней. Без аналитики и трендов — просто столбики.

### 11.9 Лаборатория (только админ)

**FR-LAB-1.** Сводка по моделям за период: число распознаваний, средняя латентность, средняя стоимость (факт / гипотетически напрямую / коэффициент наценки), медианное отклонение по весу и калориям от пользовательской версии, precision/recall по ингредиентам.
**FR-LAB-2.** Сводка по гипотезам H4 и H6:
  - MAPE веса при `had_reference = true` vs `false`;
  - MAPE веса в разрезе `scale_mode` (reference / container / prior);
  - MAPE веса в разрезе `prompt_version` (v1-plain / v2-scale);
  - доля ответов с несогласованной масштабной цепочкой по каждой модели (§7.5.2);
  - средняя `scale_size_error` — насколько модель ошибается в размере самого эталона;
  - точность детекции эталонов: совпадение `scale_references` модели с `reference_objects` пользователя.
**FR-LAB-3.** Сводка по H2: доля ингредиентов, оставленных без правки, против доли приёмов пищи с правкой веса.
**FR-LAB-4.** Кнопка выгрузки всего датасета в CSV/JSON (meals + recognitions + items + evidence).
**FR-LAB-5.** Суммарные расходы за период.

Экран внутренний, но выполняется в той же дизайн-системе, что и остальное приложение (§13). Внутренний не значит неряшливый: этим экраном вы будете пользоваться чаще всех остальных, и читаемость таблиц здесь напрямую влияет на скорость выводов. Часть метрик допустимо не выносить в интерфейс вовсе, а считать SQL-вьюхами и смотреть прямо в Supabase — но то, что вынесено, должно быть сделано аккуратно.

## 12. Аналитические представления

Заложить как SQL-вьюхи сразу — они и есть результат всего прототипа.

```sql
-- Отклонение модели от пользовательской версии по каждому приёму пищи
create view v_model_vs_user as
select
  r.id as recognition_id,
  r.meal_id,
  r.model_id,
  r.is_primary,
  r.total_weight_g                       as model_weight_g,
  u.user_weight_g,
  r.total_weight_g - u.user_weight_g     as weight_delta_g,
  case when u.user_weight_g > 0
       then abs(r.total_weight_g - u.user_weight_g) / u.user_weight_g
  end                                    as weight_ape,
  (r.nutrition_catalog->>'energy_kcal')::numeric  as model_kcal,
  u.user_kcal,
  case when u.user_kcal > 0
       then abs((r.nutrition_catalog->>'energy_kcal')::numeric - u.user_kcal) / u.user_kcal
  end                                    as kcal_ape,
  r.cost_rub_actual,
  r.cost_direct_usd,
  r.latency_ms,
  r.has_scale_ref,
  r.scale_mode,
  r.scale_size_error,
  we.had_reference,
  we.method                              as weight_method
from recognitions r
join (
  select meal_id,
         sum(weight_g) as user_weight_g,
         sum(weight_g * coalesce(kcal_per_100g, 0) / 100) as user_kcal
  from meal_items_with_nutrition          -- вспомогательная вьюха
  group by meal_id
) u on u.meal_id = r.meal_id
left join weight_evidence we on we.meal_id = r.meal_id
where r.status = 'ok';

-- Качество состава: сколько позиций модели пользователь оставил как есть
create view v_ingredient_agreement as
select
  m.id as meal_id,
  count(*) filter (where mi.origin = 'model_kept')    as kept,
  count(*) filter (where mi.origin = 'model_edited')  as edited,
  count(*) filter (where mi.origin = 'user_added')    as added,
  (select count(*) from meal_removed_items r where r.meal_id = m.id) as removed
from meals m
join meal_items mi on mi.meal_id = m.id
group by m.id;
```

Метрики, которые считаем из этих вьюх:
- **MAPE веса** и **MAPE калорий** по каждой модели.
- **Ingredient precision** = kept+edited / (kept+edited+removed); **recall** = kept+edited / (kept+edited+added).
- **Стоимость на одно распознавание** — двумя независимыми колонками: факт в рублях и гипотетически напрямую в долларах.
- **Эффект эталона (H4):** MAPE веса при `had_reference = true` против `false`, и в разрезе `scale_mode`.
- **Эффект масштабной цепочки (H6):** MAPE веса в разрезе `prompt_version`.
- **Согласованность цепочки:** доля ответов, где арифметика `scale_chain` не сходится сама с собой (§7.5.2) — по каждой модели.
- **Точность распознавания эталона:** средняя `scale_size_error` и пересечение `scale_references` модели с `reference_objects` пользователя.

## 13. Дизайн-система

Прототип — не повод для неопрятного интерфейса. Тестировщики — живые люди из вашего окружения, и если приложением неприятно пользоваться, они бросят его на третий день, а вы получите не отрицательный ответ на гипотезу, а отсутствие данных. Опрятность интерфейса здесь — часть методологии, а не эстетическая прихоть.

При этом собственный визуальный язык мы не изобретаем: у прототипа нет задачи запомниться. Берём готовую, проверенную систему и аккуратно её применяем.

### 13.1 Источник дизайна

**Основа — Apple Human Interface Guidelines** (`developer.apple.com/design/human-interface-guidelines`). Причины: приложение мобильное и в первую очередь будет открываться с iPhone; HIG — самая подробно документированная и стабильная из публичных систем; её решения по спискам, формам, модальным окнам и навигации закрывают ровно те задачи, которые у нас есть.

**Макеты для сверки — Apple Design Resources** (`developer.apple.com/design/resources`): бесплатные библиотеки компонентов для Figma и Sketch. Используются как эталон при разметке, не как исходники для копирования.

### 13.2 Библиотека компонентов

**Konsta UI v5** — MIT, построена на Tailwind CSS v4, даёт готовую iOS-тему (актуализирована под внешний вид iOS 26), официально поддерживает React и работает с Next.js SSR без дополнительной настройки. Версия 5.2.0 от 29 июня 2026 — библиотека живая.

Это закрывает почти весь наш набор: списки-группы, навбар, таббар, кнопки, сегментед-контролы, шиты, диалоги, поля ввода, свитчи, слайдеры, скелетоны. Ровно то, из чего состоят экраны §11.

Устанавливается одной строкой: `npm i konsta`. Кастомизация — через обычные классы Tailwind, то есть при необходимости отойти от iOS-вида это делается локально, без борьбы с библиотекой.

### 13.3 Типографика

**Не скачиваем и не бандлим SF Pro.** Лицензия Apple на этот шрифт разрешает использование только для создания макетов интерфейсов приложений под платформы Apple; класть файл шрифта в веб-приложение она не разрешает.

Правильный и полностью легальный способ получить ровно тот же вид — системный шрифтовой стек. На iPhone и Mac браузер сам отрисует San Francisco, на Android — Roboto, на Windows — Segoe UI. Это стандартный механизм, который Apple сама рекомендует для веба:

```css
font-family: system-ui, -apple-system, "Segoe UI", Roboto,
             "Helvetica Neue", Arial, sans-serif;
```

Числа в таблицах и нутриентных панелях — табличными цифрами, иначе колонки будут «плясать»:

```css
font-variant-numeric: tabular-nums;
```

Шкала типографики — из HIG: заголовок экрана 34/41, заголовок секции 20/25, основной текст 17/22, подпись 13/18, мелкая подпись 11/13. Держим её единой на всех экранах, включая административный.

### 13.4 Иконки

**Не используем SF Symbols** — их лицензия ограничивает применение интерфейсами приложений под iOS, iPadOS, macOS, tvOS и watchOS, а веб-приложение под это не подпадает.

Берём **Lucide** (MIT, ~1500 иконок, есть пакет `lucide-react`). Стилистически он достаточно нейтрален, чтобы не спорить с iOS-темой Konsta. Один набор на всё приложение, толщина линии единая.

### 13.5 Цвет

Семантическая палитра, а не набор произвольных значений. За основу — системные цвета iOS:

| Роль | Светлая тема | Тёмная тема | Где применяется |
|---|---|---|---|
| Акцент | `#007AFF` | `#0A84FF` | кнопки, ссылки, активные состояния |
| Успех / подтверждено | `#34C759` | `#30D158` | подтверждённые человеком значения |
| Предупреждение / оценка | `#FF9500` | `#FF9F0A` | оценки модели, несогласованная цепочка |
| Ошибка | `#FF3B30` | `#FF453A` | неудачное распознавание, удаление |
| Фон экрана | `#F2F2F7` | `#000000` | подложка |
| Фон карточки | `#FFFFFF` | `#1C1C1E` | группы списков, карточки |
| Основной текст | `#000000` | `#FFFFFF` | |
| Вторичный текст | `#3C3C4399` | `#EBEBF599` | подписи, единицы измерения |

Тёмная тема — обязательна и делается автоматически через `prefers-color-scheme`. Отдельного переключателя в MVP нет.

### 13.6 Визуальный язык достоверности

Это единственное место, где мы отходим от стандартной iOS-раскладки и добавляем своё. И добавляем не ради красоты: **степень достоверности числа — главное содержание этого продукта**, и она обязана быть видна без чтения.

Три состояния, единые на всех экранах:

| Состояние | Оформление | Значение |
|---|---|---|
| **Оценка модели** | значение в оранжевом, префикс `≈`, шрифт обычного начертания | число пришло от модели, человек его не трогал |
| **Подтверждено человеком** | значение чёрным, обычным начертанием, без префикса | человек посмотрел и оставил как есть |
| **Исправлено человеком** | значение чёрным полужирным, рядом мелкой вторичной подписью зачёркнутое исходное | человек изменил значение модели |

Тот же принцип распространяется на нутриенты: значение, посчитанное по справочнику, показывается обычным текстом; значение, взятое из оценки самой модели (`nutrition_source = 'model'`, §8.4), — с префиксом `≈` и в оранжевом.

Правило, из которого всё это следует: **пользователь в любой момент должен видеть, чему он смотрит в глаза — измерению или догадке.** Ни одна цифра в интерфейсе не имеет права выглядеть достовернее, чем она есть.

### 13.7 Раскладка и физические ограничения

- Нижний таббар из трёх вкладок: «Сегодня», «История», «Профиль». Кнопка съёмки — крупная, на экране «Сегодня», в зоне большого пальца.
- Минимальная область нажатия — 44 × 44 px (требование HIG). Особенно важно для полей веса на экране правки, где пальцем целятся в мелкие числа.
- Учёт вырезов и жестовой полосы: `env(safe-area-inset-top)` и `env(safe-area-inset-bottom)`. Без этого в standalone-режиме PWA на iPhone нижняя панель уедет под системную полосу.
- `viewport-fit=cover` в мета-теге viewport.
- Все числовые поля — `inputmode="decimal"`, чтобы вызывалась цифровая клавиатура.
- Списки ингредиентов — сгруппированные списки в стиле iOS (`Konsta List` / `ListItem`), а не таблицы: на телефоне таблицы нечитаемы.

### 13.8 Состояния загрузки, пустоты и ошибок

- **Загрузка:** скелетоны на месте будущего контента, не спиннер по центру. На экране распознавания — прогресс с названием модели и честной оценкой времени.
- **Пусто:** экран без приёмов пищи говорит, что делать, а не констатирует пустоту. «Сфотографируйте первое блюдо» и кнопка — а не «Нет данных».
- **Ошибка:** сообщение объясняет, что произошло и что делать. «Модель не ответила. Попробуйте ещё раз или введите состав вручную» — а не «Ошибка 500».
- Глаголы в кнопках совпадают с результатом: кнопка «Сохранить» приводит к сообщению «Сохранено».

### 13.9 Порог качества

Выполняется всегда, отдельными требованиями не оговаривается:
- видимый фокус с клавиатуры на всех интерактивных элементах;
- уважение `prefers-reduced-motion` — при включённом отключаем переходы;
- контраст текста не ниже 4.5:1;
- корректная работа при системном увеличении шрифта;
- никакой анимации ради анимации: переходы между экранами и появление шита — да, декоративные эффекты — нет.

### 13.10 Административный экран

Та же дизайн-система, тот же шрифт, та же палитра. Отличия только функциональные: горизонтально прокручиваемые таблицы с закреплённой первой колонкой, табличные цифры, сортировка по клику на заголовок. Числа выравниваются по правому краю, единицы измерения — вторичным цветом.

## 16. Риски

| Риск | Вероятность | Что делаем |
|---|---|---|
| Supabase Free засыпает через 7 дней | высокая | Cron-пинг раз в 3 дня с самого начала |
| Vercel/Supabase недоступны из РФ | средняя | Проверить на этапе 0; план Б — Timeweb Cloud / Selectel |
| Vercel Hobby — некоммерческое использование | средняя | Для внутреннего теста допустимо; переход на Pro при любой монетизации |
| ID моделей на polza.ai меняются / модель отключают | высокая | Конфиг с `enabled`, ежедневная сверка с `/v1/models/catalog`, обработка 404 |
| `strict: true` не поддерживается частью моделей | средняя | Фолбэк на `json_object` + валидация схемы на бэкенде + одна повторная попытка |
| Плохое качество русских названий в справочнике | высокая | Ручная вычитка топ-500; механизм алиасов, самообучающийся на правках пользователей |
| Много `unmatched`-ингредиентов | высокая | Фолбэк на нутриенты от модели + понятный UX привязки к справочнику |
| Исчерпание 1 ГБ хранилища | средняя | Сжатие на клиенте, чистка оригиналов, при необходимости — вынос в Cloudflare R2 |
| Тестировщики бросают через 3 дня | высокая | Минимум трения: 2 тапа до фото, правка не обязательна, модалка «Откуда вес?» пропускаемая |
| Стоимость распознаваний выйдет за ожидания | низкая | Учёт стоимости с первого дня; при 100 распознаваний/день и ~1 ₽ за запрос — порядка 3 000 ₽/мес |

## 17. Открытые вопросы

1. **Сколько ингредиентов показывать по умолчанию?** Слишком дробный состав (12 позиций на тарелку) утомит пользователя и снизит долю правок. Предлагаю ограничить промптом: не более 10 позиций, мелочь объединять. Нужно ваше решение.
2. **Пропорциональный пересчёт при правке общего веса** (FR-EDIT-5) — включать по умолчанию или спрашивать каждый раз?
3. **Нужен ли ручной ввод блюда без фото?** Это резко повысит шанс, что тестировщики продержатся дольше недели, но добавит экран. Пока не заложено.
4. **Несколько фото одного блюда** (сверху + под углом) — заметно улучшает оценку объёма в исследованиях, но усложняет UX. В MVP — одно фото. Стоит ли закладывать поле под массив?
5. **Норма суточного потребления** — одна общая или спрашивать пол и возраст при заведении пользователя? Пока заложена общая.
6. **Кто делает импорт и русификацию справочника** — это самая трудоёмкая разовая задача (этап 0.5), и она блокирует всё остальное.
7. **Часовой пояс** для определения «дня» — брать из профиля или из браузера? Заложен профиль с дефолтом Europe/Moscow.
8. **Насколько настойчиво просить положить карту в кадр?** Если делать это обязательным шагом — данные для H4 будут чистыми, но трение вырастет и тестировщики отвалятся быстрее. Предлагаю: подсказка без принуждения, но раз в неделю — напоминание «сегодня попробуйте с картой». Нужно ваше решение.
9. **Переходить ли к схеме C (bbox + расчёт масштаба на бэкенде)?** Она достовернее, но работает не на всех моделях одинаково и ломает равные условия сравнения. Предлагаю решать по результатам метрики согласованности цепочки: если модели массово имитируют расчёт — схема C становится обязательной.
